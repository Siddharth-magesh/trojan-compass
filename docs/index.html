The problem

The answers exist. They're just scattered.

A new USC student plans courses in one system, registers in another, pays in a third and finds jobs, health services, events and visa rules somewhere else again. Each portal has its own login, layout and vocabulary. General-purpose chatbots don't solve it: they don't know this term's sections or a lab's current recruitment status, and they know nothing about the student asking. International students feel it most, because a wrong answer about work hours, insurance or registration has real consequences.

12quick links on USC's own "My Favorite Student Resources" page, each opening a different site
65official USC sources we registered and verified for the prototype alone
4+domains a first-semester question can span: academics, careers, services, housing
1conversation is all it should take

Technical deep dive

How it works under the hood

The design principles: models plan and write, while code decides what is true and who can see it. Every layer can be tested, measured and replaced on its own.

LangGraph · supervisor + parallel agents

Multi-agent orchestration

A supervisor turns each message into a JSON plan that is validated in code, then fans out to domain agents in parallel. Results are normalized, merged and verified before a writer composes the answer.

Input guard→Planner→Agents ∥→Aggregate→Verify→Synthesize→Output guard
  • Clarification exit: one short question with answer chips instead of a guess.
  • Agents are specs (prompt, allowed tools, categories): new domains plug in without changing the graph.
  • Per-request LLM call caps, at most 3 tool calls per agent, timeouts and a safe fallback path.
  • Progress streams to the UI as Server-Sent Events, so students watch each step.
Typed tools · allow-lists · identity from JWT

Controlled tools, deterministic verification

Agents never touch data directly. Every call goes through a registry that checks the agent's allow-list and validates arguments with Pydantic. The student's identity is injected by code, never chosen by the model.

  • Structured tools: course search with section and conflict checks, prerequisite status, labs, opportunities, services, checklists.
  • The verifier re-reads every card field and number from the source records. Stale or unverifiable facts are flagged or dropped.
  • Unknowns travel to the writer explicitly, so the answer says "not listed" instead of inventing.
Pinecone · BGE-small ONNX · BM25 · zero LLM calls

Hybrid, permission-aware retrieval

Guides and policies are searched by a deterministic service that returns an evidence package and decides whether the evidence is sufficient. It makes no LLM calls.

Parse→Filters→Route→Dense + sparse→Dedupe→Rerank→Validate→Package
  • Dense BGE-small (384-dim) embeddings plus BM25 sparse vectors. Alpha 0.75 for meaning, 0.25 for code- and acronym-heavy queries (CPT, I-20).
  • Filters are built only in code: public and verified data, the right academic year, the BM25 version hash.
  • Heuristic rerank favours official, fresh and year-matched sources; context expansion adds neighbouring chunks.
  • A calibrated sufficiency threshold abstains instead of answering from weak evidence.
Groq · gpt-oss-120b · Gemini fallback · cache

Centralized model gateway

Every model call goes through one gateway: provider choice, timeouts, call caps, a bounded retry on rate limits, JSON validation and usage accounting.

  • OpenAI-compatible providers: Groq openai/gpt-oss-120b primary, Google Gemini fallback.
  • Mock, cache and live modes. The cache key covers model, messages and tools, so changed facts mean a fresh answer.
  • Vision: sensitivity routing, so student data only goes to approved, contracted models; per-user quotas; model tiering by task.
Source-linked · year-versioned · schema-validated

Data that keeps its provenance

USC information is collected from official sources and stored with its source, academic year and verification date. Only verified, public data is ever used.

  • JSON records for exact facts (courses, sections, labs, services) and source-linked Markdown guides for rules and procedures.
  • A registry of categories, sources and source checks; JSON Schemas for metadata and every record type.
  • Chunks, outlines and a records index are built deterministically and parity-checked against the vectors in Pinecone.
Guards · ownership · redaction · logs without content

Security by design

Defense in depth from the edge to the answer, starting with the controls that matter most for student data.

  • The input guard blocks prompt injection before any model call; blocked requests make zero LLM calls.
  • Session ownership: one student asking for another's session gets 404, which doesn't reveal that it exists.
  • The output guard redacts SSN-like numbers and personal emails, removes non-allow-listed links and keeps official USC links.
  • One JSON log line per request (route, timings, LLM calls, guard events), never the message text.
  • Synthetic students only in the prototype; keys only in an untracked environment file.

Shipped in the prototype

  • Multi-agent graph: planner, academic, career, student-services and housing agents, verification, synthesis, guards.
  • Chat app: live agent timeline, Markdown answers with numbered citations, course, lab, service and checklist cards, schedule grid, history and a phone layout.

Roadmap

From hackathon to campus

Security and scope grow together: synthetic data now, a guarded pilot next, a hardened service after that.

Now

Hackathon prototype

  • Courses, sections, research labs, career resources and international-student guides
  • Multi-agent orchestration with verification and guards
  • Hybrid retrieval, evaluated on golden questions
  • Synthetic students, DEMO label, measured cost
Next · pilot

One-semester pilot

  • USC SSO sign-in and real, student-editable profiles
  • Housing listings and the academic calendar
  • Proactive deadline reminders
  • Chinese and Hindi, plus voice input
  • Penetration test and FERPA review, small student cohort
Later · production

Campus-wide service

  • All schools, terms and student services
  • Authorized integrations (registration, billing) behind human approval
  • WAF, MFA, SIEM, SOC 2 controls and an incident plan
  • Postgres with row-level security, autoscaling, per-student caching
  • Continuous evaluation of groundedness in CI
